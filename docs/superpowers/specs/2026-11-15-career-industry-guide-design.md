# 职业行业研究网站设计说明

- 文档路径：`docs/superpowers/specs/2026-11-15-career-industry-guide-design.md`
- 研究版本日期：2026-11-15（Asia/Shanghai）
- 文档状态：待用户审阅。本文件通过后才能编写实现计划或应用代码
- 仓库状态：私有。本阶段不启用 GitHub Pages，不配置自动部署，不将仓库改为公开

## 1. 背景与目的

用户希望把两份研究提示词所服务的任务做成可长期更新、可比较、可分享的 GitHub Pages 站点。两份提示词本身不进入仓库。一份规定行业研究的方法与质量要求，另一份要求在中国大陆找出约十个适合人文社科背景进入、并兼顾市场规模、增长和竞争格局的行业。

双方已同意：先用两到三个行业样本检验比较结构，再决定网站形态。当前三个样本是广告营销服务、养老服务、国内旅游服务。它们用来对照不同的需求来源、岗位类型和盈利条件，不是最佳行业名单，也不是完整十名排名。

本站点的成功标准是：访问者能在同一套结构下看清某个行业是否真有适合自己的岗位入口，以及证据走到哪一步。它不保证录用，也不用行业增长代替就业结论。

## 2. 已确认需求

1. 做一个轻量、中文、可在手机上阅读的职业行业研究静态网站。
2. 首页比较上述三个样本，展示需求、岗位入口、盈利与稳定性、主要风险和证据缺口。
3. 提供行业页、岗位页、来源与方法页，结构和用语保持一致。
4. 支持按岗位方向筛选，筛选结果必须来自已录入的结构化数据，不能临时编造匹配项。
5. 不做缺乏依据的综合评分、推荐指数或自动排名。
6. 所有具体数字都要标明年份、统计或披露口径、来源名称和 URL。来源冲突时保留不同口径，不擅自平均成一个权威数字。
7. 没有可靠证据的项目必须明示缺失，不得编造集中度、在招职位、薪资、就业人数或文科岗位占比。
8. 必须标明：截至 2026-11-15 的研究中，公开招聘岗位的活页核验尚未完整。
9. 页脚或首页显著位置说明：这是初步研究，不是就业保证，网站尚未正式上线。
10. 最终面向 GitHub Pages，但当前仓库保持私有，暂不公开发布，也不在本阶段打开 Pages。
11. 未来应用代码放在 `src/`。内容数据与界面分离。站点数据使用结构化 JSON，不使用 CSV 作为站点数据源。Parquet 只用于日后可能出现的批量研究数据，不进入本阶段站点。

## 3. 范围与非目标

### 3.1 本轮实现获准后的范围

实现阶段只做静态站点初版，内容仅覆盖 2026-11-15 已完成的三个行业样本，以及这些样本中已经出现的文科相关岗位类型。页面在本地构建后即可预览。仓库继续私有。部署若发生，也只能在用户再次明确批准后手动进行。

### 3.2 明确排除

- 不在本设计获准前编写应用代码、搭建项目脚手架或启用部署
- 不把行业样本扩展到十个，除非后续另有研究与规格更新
- 不复制两份原始提示词文档，不上传附件、凭证、隐私材料或未公开个人数据
- 不做用户登录、评论、后台、数据库、搜索服务或个性化推荐
- 不接入实时招聘平台，不自动抓取在招职位，不显示未完成活页核验的职位，如同它们已被核实
- 不提供职业测评、简历投递、薪资计算器或录取预测
- 不输出 CR、HHI 或其他看起来完整、实际没有可靠口径的集中度数字
- 不把护理员等技术或照护岗位算作文科对口岗位，除非页面明确将其标为相邻而非对口
- 不在本阶段启用 GitHub Actions 自动发布，不修改仓库可见性
- 不把咨询公司付费报告摘要写成全文结论

## 4. 架构方案比较与推荐

本项目是内容主导的静态网站，需要稳定的引用、可维护的数据和较低的运行负担。以下三个方案都满足“静态输出、无登录后端”这一底线，差异主要在类型约束、内容组织和以后扩展到 GitHub Pages 的成本。

### 方案 A. Astro 与 TypeScript 静态输出（推荐）

用 Astro 在构建时生成静态 HTML。页面、组件和校验逻辑使用 TypeScript。行业、岗位、指标和来源放在 `src/data/` 的 JSON 中，由构建脚本或页面读取，不把正文写死在组件里。

优点是默认少用客户端 JavaScript，适合阅读型页面。内容与界面分离后，更新一条口径或来源不必改布局。TypeScript 可以对必填字段、来源引用和“缺失”状态做约束，降低把空值渲染成精确数字的风险。构建产物是普通静态文件，以后手工发布到 GitHub Pages 时不必引入服务器。

代价是需要 Node.js 工具链，比纯手工 HTML 多一次项目初始化。对当前三个行业、十余个岗位规模来说，这个代价可以接受。

### 方案 B. Eleventy 加 Markdown

用 Eleventy 把 Markdown 和数据文件编译成静态页。上手快，依赖较少，也适合内容站。

不足是默认缺少与 TypeScript 同等的数据结构约束，筛选逻辑和引用完整性要靠约定和额外测试来补。以后若增加指标字段或核验状态，更容易出现页面与数据不一致。对强调口径和缺数据明示的项目，这个风险高于方案 A。

### 方案 C. Vite 多页或 Next.js 静态导出

Vite 多页可以输出静态 HTML，但内容集合、页面路由和数据校验通常要自己搭。Next.js 静态导出能力强，但框架体量和概念对一个无后端的研究站偏重，也更容易把后续需求带向服务端功能。若做成单页应用，首屏和分享链接都不如预渲染文档页稳定。

不推荐把本项目做成纯客户端路由的单页应用。

### 推荐

采用方案 A。实现阶段初始化 Astro 与 TypeScript，`outDir` 指向纯静态目录。所有应用代码位于 `src/`。站点运行时数据只用结构化 JSON。CSV 不作为站点输入。若日后做大规模原始研究底稿，可用 Parquet 存放在研究流程中，再导出为站点 JSON，而不是让页面直接读取 Parquet。

本文件已给出推荐，实现计划不再就框架选择向用户重新提问，除非审阅规格时要求更换方案。

## 5. 信息架构与页面行为

站点使用中文路径或中文标题加稳定英文 slug。推荐使用英文 slug，避免托管和链接编码问题：

- `/` 首页
- `/industries/advertising/` 广告营销服务
- `/industries/elderly-care/` 养老服务
- `/industries/domestic-tourism/` 国内旅游服务
- `/roles/{role-slug}/` 岗位页
- `/methods/` 来源与方法

所有页面共享页头、页脚和“初步研究，不是就业保证”的说明。页脚固定展示研究版本日期 2026-11-15（Asia/Shanghai），以及“尚未正式上线”。

### 5.1 首页

首页先用一段话说明选样理由：三个样本用于比较，不是排名。随后给出比较区。桌面端可用表格，窄屏改为卡片堆叠，避免只能横向拖动才能读完一行。比较维度固定为：行业定义、需求证据、适合的文科岗位、入口与地域限制、盈利与稳定性、主要风险、证据缺口。不设总分，不设红绿灯综合评级。

岗位方向筛选放在比较区上方。初版提供互斥筛选，选项为：

- 全部
- 营销传播（客户执行、策略、公关、活动、内容、品牌宣传等）
- 社会服务与社区活动（社工、文娱活动、生活管家、社区运营等）
- 目的地与旅游产品（目的地运营、旅游产品策划、景区营销、旅游内容等）

选择某一方向后，比较区只保留至少包含该方向岗位的行业，其下同时列出匹配岗位并链到岗位页。若某行业完全没有该方向岗位，则从当前比较结果中隐藏，不补充虚构岗位。若筛选后没有结果，显示空状态文案，例如“当前方向在已录入的三个样本中没有匹配岗位”，并提供恢复“全部”的操作。筛选不改变 URL 必需结构，但可以用查询参数如 `?direction=marketing` 保持可分享。该筛选在构建后的静态页中用少量客户端脚本完成即可，并保证无脚本时仍能阅读完整比较内容。

### 5.2 行业页

三个行业页使用同一模板，顺序为：定义与口径、需求证据、适合岗位、日常工作概况、入口门槛、可做的小作品或技能准备、地域与资历限制、盈利与稳定性、风险、尚未证实的问题、来源列表。每个数字旁边给出年份、口径和链接。适合岗位链到岗位页。对“行业在增长因此更好找工作”这类推断，页面必须分开写证据和判断，不能写成既成事实。

### 5.3 岗位页

岗位页说明该岗位做什么、常见准备材料、在哪些样本行业出现，以及核验状态。核验状态只允许使用以下三档：

- 已完成活页核验：同时提供雇主、标题、链接和核验日期
- 仅见招聘或年报材料：例如高校就业网转载、公司年报中的业务描述，必须写明材料性质和限制
- 尚未核验：不得写成像正在招聘一样

截至 2026-11-15，多数岗位应标为“仅见招聘或年报材料”或“尚未核验”。泰康之家社工、文娱活动、管家、市场营销等，可见于南开大学就业网转载的 2027 届校园招聘材料，官方招聘门户当时未能完成抓取，因此不得标成已完成活页核验。蓝色光标相关岗位主要依据年报业务构成。携程可见官方招聘入口和高校转载的校园招聘信息，具体产品或目的地运营职位描述未完成活页核验。

### 5.4 来源与方法页

该页说明研究目的、地理范围（中国大陆）、资料时点、来源优先级（统计局、监管部门、行业协会、公司年报和官网，其次才是可核验的新闻转述，付费摘要只作线索）、口径规则、更新方式，以及当前未核实清单。方法页可以概括研究原则，但不粘贴原始提示词全文。未核实清单至少包括：三个行业的可靠薪资、官方集中度、全国养老服务营业收入、广告业从业人员完整时序、旅行社与景区用工结构，以及多数岗位的官网在招活页。

## 6. 数据模型、口径与引用

实现阶段在 `src/data/` 放置 JSON，并用 TypeScript 类型描述形状。推荐拆为 `meta.json`、`industries.json`、`roles.json`、`metrics.json`、`sources.json`，用稳定 `id` 互相引用。一条指标至少包含：所属行业或岗位、名称、数值或缺失标记、单位、年份或起止年份、地理范围、口径说明、数据性质（官方统计、机构估算、企业披露、自行测算、预测）、来源 `id`、可选注释。自行测算必须写出公式，例如 2025 年国内旅游人均单次花费为当年出游总花费除以出游人次。

来源记录至少包含：机构或作者、文献或页面名称、发布或访问日期、URL、以及它支持哪几条指标或判断。页面不得只在文末堆一组无法对应的链接。

数据性质不允许被页面样式放大成比实际更高的精确度。例如限额以上单位零售额不得写成全市场零售额，广告业务收入不得默认等同代理公司净利润，国内游客出游总花费不得写成旅行社或景区收入。

允许写入初版的研究结论，必须保持既有限制，包括但不限于：

- 广告业：2024 年事业单位和规模以上企业广告业务收入 15464.1 亿元、增长 17.9%，互联网发布收入占发布环节 86.5%。2025 年同口径收入 20502.1 亿元、增长 32.6%。蓝色光标 2025 年营收与利润若采用媒体转述，必须标明转述关系，并链接年报页面。不得把净利率写成官方公布值。若展示约 0.33% 的净利率，必须标明这是根据已披露营收和归母净利润自行测算。
- 养老服务：使用人口和机构、床位等供给指标，不得填写一个未经官方公布的全行业营业收入。2025 年 60 岁及以上人口 32338 万人，与机构和床位较 2024 年下降的对比可以保留，但下降原因标为尚未证实。若展示注册机构床位使用率约 45.4%，必须说明这是把 2024 年末服务人数近似为在住人数后的自行测算，定义待核实。
- 国内旅游：2024 年和 2025 年出游人次与花费可以引用统计公报。人均单次花费下降必须标为自行测算。宋城演艺营业收入下降、众信旅游归母净利润下降、携程净营业收入增长和投资利得影响，应作为企业分化证据，不得推广为全行业利润结论。

以后更新研究时，先改 JSON 和来源，再构建，并在 `meta` 中更新研究版本日期。不得静默覆盖旧口径。

## 7. 无数据与错误行为

缺失值在数据里用显式状态表示，例如 `unavailable`（没有找到可靠数据）或 `unverified`（有线索但未核实），页面渲染为“暂无可靠数据”或“尚未核实”，而不是 `0`、空白或占位评分。

构建时若某条指标有数值却没有来源、年份或口径，构建应当失败。若岗位状态写成“已完成活页核验”却缺少核验日期或链接，构建也应当失败。这是防止把不完整研究填进页面的硬约束。

用户侧筛选无结果时，显示空状态和恢复全部的操作，不回退到伪造列表。页面或资源不存在时，提供简洁的静态 404 页，链回首页和来源与方法页。本阶段没有后端，因此不涉及认证错误或接口超时。若本地预览或日后托管失败，不得用临时示例数据顶上线。

## 8. 移动端与无障碍

目标是在常见手机宽度（以 375 像素宽为手工检查基准）上可以完整阅读，不出现必须放大才能看清的正文，也不把关键比较内容只放在宽表格里。正文与背景对比度需达到可阅读水平。站点语言为 `zh-CN`。

使用语义标题、主要地标和可见的焦点样式。筛选控件要有明确标签，键盘可以操作，选项变化不仅靠颜色区分。装饰性图片可为空替代文本。内容性图或链接需要短替代文本或可访问名称。尊重系统的减少动态效果设置，不把信息只放在悬停状态里。不自动播放媒体。初版不依赖复杂动画。

## 9. 测试与完成标准

实现阶段的完成，以本地验证为准，不以已经公开发布为准。至少包括：

- TypeScript 检查和生产构建通过，输出纯静态文件
- 约定路由均可打开：首页、三个行业页、已录入岗位页、来源与方法页、404
- 筛选逻辑测试覆盖“全部”、三个方向，以及无匹配时的空状态
- 无数据状态测试覆盖缺失指标不会被渲染成数字或分数
- 校验测试覆盖“有数值无来源则构建失败”
- 行业页、岗位页和来源记录之间的链接可以互相到达
- 在 375 像素宽度下手工检查首页比较区和筛选控件
- 页面含研究版本日期、非就业保证说明，以及招聘核验尚未完整的提示

未完成上述项，不得声称初版已完成。本阶段测试不要求启用 GitHub Actions 部署，也不要求在线 Pages 预览。

## 10. 安全、隐私与发布边界

仓库保持私有。本设计审阅阶段和随后的实现阶段，默认都不启用 GitHub Pages，不添加用于发布的 GitHub Actions，不把仓库改为公开。若以后需要预览或发布，必须由用户另行批准具体方式。私有仓库的 GitHub Pages 可能受 GitHub 套餐限制，批准发布前应再确认账号是否具备该能力，但确认不等于现在打开开关。

获准后的首次发布方式应是手动发布经过构建的静态文件，或在单独批准后再增加受约束的工作流。工作流若出现，也只能发布构建产物，不能把研究原始附件、密钥或本机环境文件带上网。仓库中不存放密钥、登录状态、原始提示词文档和个人隐私材料。

在仓库仍为私有且 Pages 未开启时，PR 和本地预览是唯一的审阅面。不要把未审阅的设计分支直接合并后当作已上线产品对外引用。
